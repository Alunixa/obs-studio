# Alunixa OBS：2026-09-10 上游同步与稳定性修复

## 本次追加：单文件缓存，保存成功后再回收

用户确认回放必须连续保留最近的时间窗口，不能在每次保存后从零累计。
本次替换了初版的独立临时分块文件，采用：

- 每个缓存实例只有一个 `OBS-Replay-Cache/<独立会话 ID>/cache.tmp`，
  录像目录不再散落大量 tmp；内部 16 MiB 区段只是同一文件中的范围。
- 点击保存时 flush 当前区段并持有保存令牌，后续数据继续写入同一个文件；
  新过期区段只进入待回收队列，保存期间不释放其空间，也不覆盖复用。
  保存开始前就已空闲的区段可以继续写入，不涉及删除受保护数据，避免
  非稀疏磁盘每保存一次就永久增长文件。
- 实时回放索引仍按原时间/容量窗口滚动，所以连续保存仍包含上次保存前
  尚在窗口内的画面；冻结的是物理回收，不是时间窗口或录制。
- 完整快照一直保留到 muxer 关闭文件并返回成功，之后才回收不再被
  当前窗口或任何读者引用的区段；不会读完一个包就提前释放。
- Windows 支持稀疏文件的文件系统使用 `FSCTL_SET_ZERO_DATA` 回收过期区段
  的实际占用，活跃数据不搬动；已释放区段循环复用，避免平时无限追加。
  稀疏文件的逻辑长度与“占用空间”不同；不支持稀疏回收时仍使用单文件
  空闲区段复用，历史最大分配可能保留到停止缓存，不退回一堆小文件。
- 保存失败不恢复物理回收、不发成功事件、不停止正常缓存写入；界面显示
  保存失败，修复输出问题后可重试。重试成功或用户主动停止后再释放。
  保存期间及连续失败期间的磁盘占用可暂时超过目标窗口，但受下面的
  安全预算和剩余空间检查约束，不能宣称硬性零超额或无限保护。
- 连续保存使用不覆盖的文件名，即使同一秒或使用固定文件名格式也保留
  多次成功保存的文件，不覆盖上一份视频。

新增回归覆盖单文件数量、暂停回收期间数据不变、失败不回收、成功重试只
释放过期区段、空闲区段循环复用，以及停止/重启期间仍在保存的文件寿命。
GPU 测试另有 `window` 模式：5 秒回放窗口，两次保存仅间隔 250 ms，
再注入输出目录故障并重试；输出时长和完整解码单独核验，避免仅凭成功事件
就声称窗口没有被清零。

## 面向其他用户分发的边界

- 不硬编码盘符、用户名、GPU 或个人配置；缓存放在用户设置的录制目录下，
  每个实例使用独立会话目录，支持 UTF-8 路径，回归包含中文、空格和括号。
- 单文件稀疏能力按运行时实际接口结果启用；不可用时自动退化为区段复用，
  不是只为开发机器的 NTFS 磁盘设计。自动化测试会强制走非稀疏路径，
  验证 128 次保存后文件仍保持固定大小，且有效数据没有变化。
- 临时文件安全预算为 `2 × 配置的磁盘回放容量 + 64 MiB`；
  未提供容量时使用 2 GiB 默认预算。新建区段前检查至少保留 256 MiB
  可用空间，其他进程仍可能同时消耗空间，实际 I/O 错误也会检查。
- 识别 FAT/FAT32 后，超出其单文件范围的预算会在启动时明确报错，
  提示降低缓存容量或换用合适的录制目录，不等写到中途才静默损坏。
- 持续保存失败不会无限吃满磁盘：达到预算或剩余空间保留线时，
  停止缓存并显示具体原因。停止会释放不再被保存线程引用的数据，
  **不是无限期保留全部历史、不是断电恢复格式**。
- 正常停止只清理本会话的文件和目录；不递归删除公共缓存根目录，
  不删除其他实例的文件。异常进程终止可能留下独立会话目录，
  当前版本不宣称具有崩溃后自动恢复/清扫功能。
- RAM 模式、NVIDIA 编码和软件 x264 的验证分开进行；
  不把开发机器的一张显卡测试等同于覆盖所有 GPU、移动硬盘或网络存储。
- 分发资产由 GitHub Actions 从固定提交完整构建，不携带开发者的场景、
  配置、录制、第三方插件或测试视频；使用完整 ZIP，不以单个 DLL 补丁
  覆盖来源不一致的安装。仍以定制预发布版发布，而非冒充官方稳定版。

### 封装失败的额外修复

窗口故障测试实际发现输出文件无法打开时，muxer 清理未创建的 AVIO 上下文
可能访问空指针。本次修复初始化失败、部分资源初始化和退出清理，并将
写入、seek、trailer、最终 flush/close 及子进程异常正确传播为失败。
I/O 线程失败时唤醒等待缓冲空间的生产者，避免继续等待一个已经退出的线程。
只有封装成功完成、关闭输出且子进程成功返回，才允许释放受保护的过期区段。

新增 `test-replay-mux` 直接验证真实 helper 的私有 I/O/清理实现，
不需要 NVIDIA 或图形环境：空 AVIO、正常关闭、写入失败、seek 失败、
最终关闭失败均有可重复回归，并由 GitHub Actions 运行。

## 已验证的问题原因

### 插件加载失败

本机故障安装混合了不同批次主程序、Qt、插件和 FFmpeg DLL：

- 2026-09-10 17:34 的日志为 OBS `0.0.1`，websocket 编译 Qt `6.8.3`、
  运行 Qt `6.11.1`，多个原生插件无法加载。
- 文件检查发现，主程序/obs.dll 标记为 `0.0.1`，obs-ffmpeg/win-dshow 插件标记为 `32.0.4`。
- PE 导入表确认插件需要 `avcodec-61.dll`、`avutil-59.dll` 等文件，
  但目录中放的是 `avcodec-62.dll`、`avutil-60.dll` 等另一代依赖。
- 另一套旧定制构建的 `30.1.2` 来自本地强制版本覆盖，不代表实际源码基线。

处理方式是同一提交、同一依赖锁定版本的全量构建和完整 ZIP，
而不是把新的 DLL 单独覆盖进旧目录；CI 会真正加载关键 DLL 的导入依赖。
无 AJA/DeckLink 硬件时相应模块不初始化，与 FFmpeg 依赖缺失不是同一类错误。
第三方插件未打包，避免把旧的、不兼容的二进制重新带入。

### 回放花屏与保存错误

旧的环形临时文件可能在异步保存还未读取数据时被录制线程覆盖；
写入/读取长度和 seek 失败也未完整检查，关键帧可能被任意逐包清除。

修复后：

1. 保留磁盘回放功能，采用单个缓存文件内的 16 MiB 区段，不覆盖仍被引用的数据。
2. 保存前 flush 并封存当前区段；快照持有引用，后续录制继续，物理回收暂停。
3. 停止缓存不删除仍被保存线程读取的数据；最后一个引用释放后自动清理。
4. 多个 OBS 实例使用独立 UUID 会话目录和排他创建，不共用同一个临时文件。
5. 写入失败停止缓存，不把未写入的数据伪装成成功，也不静默退回超大 RAM 缓存。
6. 短读、封存失败、线程创建失败和 muxer 异常均走失败路径；仅实际成功才发出保存成功信号。
7. 清理缓存保留完整关键帧组，并防止超大包触发无限清理循环。

原有存储模式和配置键保持兼容；RAM 模式继续使用内存，
磁盘模式保留 8 TiB 配置上限。磁盘上限是保留窗口的目标值，
仍需至少两个关键帧组；16 MiB 分块粒度和正在保存的快照会带来临时额外占用，
保存完成后释放，不伪称所有情况下都存在硬性零超额上限。

### 编码开销与卡住

2026-09-10 15:18 日志使用 2560×1440/60fps、I444、HEVC、CQP 14、P6
和四分之一分辨率多遍编码，触发 CPU 回传路径，并报告 88.0% 编码跳帧；
17:34 的另一套程序 NVENC 探测耗时约 130 秒。

- 非纹理 NVENC 路径复用一个编码器自有锁页缓冲区，不再逐帧逐平面
  注册/注销主机内存；合并 CUDA 上传，正确处理平面 stride 和 P010 字节宽度。
- 失败路径弹出 CUDA 上下文，避免后续调用继承未清理状态。
- 不强制把 I444 改成 NV12，不改变原始像素精度、CQP、预设、帧率或用户配置。
- Windows 父进程给 NVENC 能力探测加 10 秒截止时间，覆盖 helper
  进入 main 之前或退出过程中卡住的情况；不限制正常录制/muxer 进程的运行时间。
- 正在保存大回放时重启缓存会给出明确提示，而不是在 UI 线程等待整段保存。

这些修复针对代码缺陷和已发现的调用开销，不能据此保证任意游戏负载、
驱动状态、第三方编码任务或已损坏的旧视频都会自动恢复。

## 验证方式

`ENABLE_REPLAY_TESTS=ON` 会构建 `test-replay-storage`，覆盖：

- 保存快照在停止/重启后保持字节一致；
- 慢速读线程与 2048 次新包写入/分块回收并发；
- 短读、写入失败、无效目录、超大包、未封存读取；
- 50 轮双实例启动/关闭，不残留缓存文件或 libobs 分配；
- 稀疏/非稀疏路径、128 次保存后单文件大小不增长、临时空间预算和低空间故障；
- NV12/P010/I444 内容、步长、越界及整数溢出；
- Windows 静默/部分输出的挂起子进程截止时间及正常退出。

`Verify-Runtime.ps1` 验证完整包中关键插件的真实 DLL 依赖加载。
`test-replay-mux` 验证封装失败路径和最终关闭错误不会被报告为成功。
GitHub Release 的构建信息记录精确提交、CI 运行及 ZIP 的 SHA-256；
GPU 硬件录制和长时间用户工作负载应与这些自动化检查分开记录。

### 2026-09-10 初版多文件缓存的历史实测结果

在 RTX 3060、驱动 616.86 上执行独立合成画面/音频测试，
没有使用用户的桌面、麦克风、场景配置或原始录制内容。
代码基于 `bdb4fff45` 的修复实现及 `1fb163860` 的测试兼容调整。
每组同时录制并保存两次回放，然后停止缓存与录制：

| 编码器 | 输入格式 | 缓存 | 输出像素格式 | 三个文件全程解码 |
| --- | --- | --- | --- | --- |
| NVENC HEVC | I444 | 磁盘 | yuv444p | 通过 |
| NVENC H.264 | NV12 | 磁盘 | yuv420p | 通过 |
| NVENC HEVC | P010 | 磁盘 | yuv420p10le | 通过 |
| NVENC HEVC | I444 | RAM | yuv444p | 通过 |

- 共 12 个文件，均为 2560×1440/60fps 编码测试，完整解码无错误；
  没有残留临时缓存文件，未强制降低 I444 或 P010 精度。
- 保持 CQP 14、P6、四分之一分辨率多遍编码；测试是短时合成负载，
  不是数小时游戏压力测试，也不等同于已经修复所有历史视频。
- 分块存储、并发保存、错误注入、像素布局及父进程超时回归全部通过。
- 在初始化 libobs 后，obs-ffmpeg、win-dshow、obs-nvenc、obs-webrtc、
  obs-websocket 的真实依赖加载全部通过；WebRTC 的静态 User-Agent
  初始化需要有效 OBS locale，因此检测脚本遵循真实应用的初始化顺序。
- OBS 未运行时曾测得 NVIDIA `nvcontainer` 占用约 53% Video Encode，
  本次没有关闭该进程或修改 NVIDIA 设置；该背景负载应独立于 OBS 排查。
- 对一个既有回放仅做开头、中段、末段各 8 秒的只读解码抽样，未报错，
  不据此判断用户遇到的所有花屏位置均正常，原视频未修改。

## 使用与回滚

将完整 ZIP 解压到新的空目录，不要覆盖到混装的旧 OBS 目录。
保留旧安装、配置和录制文件；第三方插件按兼容版本逐一恢复。
如需完全隔离测试，在新目录建立 `portable_mode.txt`，
配置放在新目录的 `config/obs-studio`，原 AppData 配置保持不变。

源码留档分支与留档预发布包用于回滚和对比；留档包不包含本次修复。
