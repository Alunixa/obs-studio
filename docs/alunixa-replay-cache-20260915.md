# 回放缓存有界回收与异常退出清理

## 状态

本说明对应本地修复 `8bddbe780` 和回归增强 `7857bf5ac`，尚未推送、运行新的 GitHub Actions 或发布 Release，也没有替换用户正在运行的程序，喵~

## 已确认的问题

- 旧实现一次保存失败后永久保持全局回收暂停，后续新产生且已过期的数据也不能复用，直至成功保存、主动停止或触及空间预算，喵~
- Windows 旧缓存仅由正常析构调用 unlink 删除，进程异常退出跳过析构时会遗留文件，喵~
- 两个问题均先在旧实现上用独立小规模测试重现，不能据此推断某份已经删除的用户大缓存必定由同一事件触发，喵~

## 实现变更

- 保存进行中仍保护完整快照，结束后恢复无引用区段的回收，喵~
- 首次失败额外保留一个快照及其包索引，后续失败不再叠加历史快照；后续成功或主动停止释放它，喵~
- 再次点击保存仍导出当前滚动窗口，没有新增历史失败快照的恢复界面或改变回放起点，喵~
- Windows 新缓存采用非继承的 delete-on-close 句柄，读者共享删除权限，独立文件引用在非稀疏模式也保证停止后尚在保存的数据可读，喵~
- 没有改变编码器、CBR/CQP、码率、分辨率、色彩格式或用户配置，不重新压缩回放，喵~
- 更新中英文保存失败提示，明确单份失败快照和正常滚动回收行为，喵~

## 本机验证结果

| 验证 | 结果 |
| --- | --- |
| 旧代码失败保存容量回归 | 按预期失败，退出码 1 |
| 旧代码跳过析构退出回归 | 按预期遗留 cache.tmp，退出码 1 |
| 修复后 128 次失败保存 | 稀疏、非稀疏两种路径通过，失败快照字节不变 |
| 实际 NTFS 空间回收 | 131072 → 65536 字节 |
| 停止/重启、读者引用、多实例、并发、读写故障 | 通过 |
| 跳过全部缓存析构直接退出 | cache.tmp 被系统关闭句柄后删除 |
| muxer 写入、seek、最终关闭故障传播 | 通过 |
| x264 窗口保存/失败后重试 | 4 个视频全程解码通过 |
| x264 连续四次失败后主动停止 | 3 个视频全程解码通过，停止后无缓存 |
| 同编码器普通录像与回放的包内容 | 5 份回放、1329 个视频包全部逐包 SHA-256 相同 |
| 篡改、漏包、乱序、重复前缀比较器负向自检 | 通过 |
| 相关 Release 目标严格编译 | obs-ffmpeg 与三个测试目标通过 |

两组软件编码测试都未报告编码跳帧，停止等待分别为 355/109 ms 与 371/93 ms；这不是长时间 NVENC 游戏负载的性能或视觉验收，喵~

## 边界与未完成项

- 动态花屏尚未定位，私人视频只有有限时间段的解码检查；软件合成回放包一致不能证明所有 NVENC、播放器或游戏场景正常，喵~
- 回放运行时仍需保存最近完整窗口，导出的视频与活动缓存同时占盘不是同一份文件，也不会在每次保存后清空窗口，喵~
- 保存中允许暂时共存当前窗口和受保护的快照；非稀疏文件可能保留逻辑高水位并复用空闲区段，不承诺文件显示大小立即下降，喵~
- delete-on-close 覆盖进程退出且最后句柄关闭的情况，不扫描删除旧版本遗留文件；突然断电、内核崩溃、其他进程长期持有句柄不在本轮已验证范围，喵~
- 跳过析构可能留下一层空会话目录，但测试确认不会保留本轮创建的缓存数据文件，喵~
- 正式分发前仍须更新对应分支的发布工作流、通过 GitHub Actions 构建和发布独立 Release，并注明本轮不包含已验证的花屏修复，喵~
